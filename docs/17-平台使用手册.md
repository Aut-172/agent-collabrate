# Agent Collaborate 平台使用手册

## 1. 手册说明

本手册面向使用 Agent Collaborate 进行需求拆解、任务协作和交付管理的项目 Leader 与 Member。它描述当前 MVP 管理界面的实际操作方式和权限边界。

平台负责需求编排、Design/Spec/Build Plan 生成、任务包管理、Git/CI 事实同步、通知和审计。成员仍然在自己的电脑上使用 Codex CLI 或其他 Agent 修改代码、运行测试和执行 Git 操作。平台不会访问成员本地工作区，也不会在服务器执行成员代码。

推荐的交付链路如下：

```text
注册/登录
  -> 创建或加入项目
  -> 完善项目成员画像
  -> 同步仓库索引和 Code Context
  -> 创建 Workflow
  -> 生成并确认 Design、Spec、Build Plan
  -> Leader 批准并创建 Task
  -> 负责人领取任务包并在本地开发
  -> 提交 Commit、PR（如要求）和 CI 证据
  -> 平台校验交付并完成 Task
  -> Leader 关闭 Workflow
```

## 2. 角色和权限

### 2.1 Leader

Leader 是项目治理者，也是可以被分配开发任务的项目成员。Leader 可以：

- 创建项目、邀请和移除项目成员；
- 查看和维护项目级统计、看板、通知和审计日志；
- 查看成员画像并管理自己的画像；
- 创建普通 Workflow 或“初始化工程与 CI” Workflow；
- 生成、编辑、确认 Design 和 Spec；
- 审阅、编辑、重新生成和批准 Build Plan；
- 调整任务拆分、负责人和任务分配；
- 处理 Blocker、重新分配或取消未完成任务；
- 查看 Git、Pull Request 和 CI 事实，并在满足条件后关闭 Workflow。

Leader 被分配任务时，仍须按普通负责人流程领取任务包、在任务分支开发并提交交付。

### 2.2 Member

Member 可以：

- 加入项目并填写自己的项目职责和能力画像；
- 查看自己有权限访问的 Workflow、项目级任务看板和通知；
- 查看项目内任务，但只能操作分配给自己的任务；
- 复制或下载自己负责的任务包，在本地使用 Agent 开发；
- 确认任务包并开始开发；
- 报告自己任务的 Blocker、提交交付和查看交付结果。

Member 不能批准 Build Plan、重新分配任务、处理 Blocker 或关闭 Workflow。后端会再次校验权限，不能通过修改浏览器请求绕过限制。

### 2.3 平台 Agent 和外部 Provider

平台 Agent 只负责生成结构化 Design、Spec、Build Plan 和分工建议。GitHub Provider 负责读取仓库、Commit、PR 和 Actions 事实；它不会替成员修改代码。平台生成内容必须经过服务端 Schema、状态和权限校验。

## 3. 登录和项目准备

### 3.1 登录或注册

1. 打开管理员提供的平台地址，进入“登录工作台”。
2. 已有账号时输入用户名和密码登录。
3. 没有账号时选择“没有账号？注册”，用户名使用 3-50 个字符，密码使用 8-128 个字符。
4. 注册或登录成功后会进入项目工作台。浏览器会保存当前登录凭证；不要在公共电脑上保留登录状态。

### 3.2 创建项目

Leader 登录后选择“创建项目”，填写：

- 项目名称；
- GitHub 仓库地址；
- Git Provider（当前 MVP 为 GitHub）；
- 默认分支，通常为 `main` 或 `master`。

新项目默认处于 `CI_NOT_CONFIGURED`。这表示项目尚未建立 CI 门禁，不代表代码已经通过 CI。

### 3.3 邀请成员和填写画像

在“项目成员”页面：

1. Leader 邀请成员加入项目。
2. 每名成员打开自己的成员资料，填写项目职责、技术能力、经验、希望承担的任务类型、限制和每周投入程度。
3. Leader 也必须填写自己的画像，因为 Leader 可能被分配任务。

能力画像按项目隔离。更新画像不会自动改动已批准的任务分配，但会影响尚未批准的 Build Plan 和后续分配建议。

## 4. 初始化工程和 CI

如果项目状态为 `CI_NOT_CONFIGURED`，建议先建立一次 CI Bootstrap：

1. 在“工作流”页面选择“创建工作流”。
2. 选择“初始化工程与 CI”。该入口只有项目 Leader 可用。
3. 填写工程骨架、构建命令、测试入口和首条 GitHub Actions 的验收要求。
4. 继续完成 Design、Spec 和 Build Plan。
5. 批准并创建 Bootstrap 任务。该任务固定初始分配给创建它的 Leader。
6. Leader 在本地完成最小工程和 CI 配置，提交任务分支、Commit，并按任务要求登记交付。
7. 等待平台同步并验证 Bootstrap Commit 和 CI 配置。验证成功后项目进入 `CI_REQUIRED`。

Bootstrap 不是日常修改 CI 的入口。项目已经启用 CI 后，后续修改 CI 配置应创建普通 `CHANGE` Workflow。

## 5. 创建和推进 Workflow

### 5.1 选择 Intent 级别

创建普通 Workflow 时选择：

| Intent | 适用场景 | 结果 |
|---|---|---|
| `ARCHITECTURE` | 系统、子系统、边界或约束设计 | 形成架构基线，不创建开发任务分工 |
| `FEATURE` | 可独立验收的功能或能力 | 生成任务、分配建议和交付链路 |
| `CHANGE` | 局部代码、配置或行为调整 | 通常推荐较小范围、单人或双人任务 |

填写标题、目标、约束和验收描述。描述越具体，生成的文档和任务边界越容易审阅。普通 Workflow 和 Bootstrap Workflow 可以选择是否要求 Pull Request；默认要求。Architecture Workflow 不显示该选项。

### 5.2 先准备 Code Context

生成 Design、Spec 或 Build Plan 前，项目仓库索引和当前 Workflow Code Context 必须是最新状态：

1. 在 Workflow 详情的 Code Context 区域执行“同步仓库索引”。
2. 索引完成后执行“刷新当前 Workflow Code Context”。
3. 等待两个运行状态都完成并显示 `CURRENT`。

刷新期间旧版本会标记为过期，不能作为新文档生成依据。如果生成按钮提示需要刷新 Code Context，先完成上述步骤。平台不会在缺少上下文时使用无依据的降级生成。

### 5.3 生成 Design、Spec 和 Build Plan

Workflow 详情的“AI 生成”区域会根据当前状态显示下一步操作：

- 生成 Design；
- 生成 Spec；
- 生成 Build Plan。

生成是异步操作。页面会显示预计耗时 `2-4min`、运行状态和已等待时长。请求提交后，相关按钮会禁用；Build Plan 因负责人画像或角色变化重新生成时，按钮会立即显示“生成中”并保持不可点击，直到本次 Run 结束。

生成失败时先查看错误信息和 AgentRun 状态，再使用“重新生成”或“重试本次生成”。不要在同一 Run 仍为 `QUEUED`/`RUNNING` 时重复提交。

### 5.4 审阅和确认文档

Design 和 Spec 都按版本保存。编辑并保存不会覆盖旧版本，而是生成新的用户版本。

部分选择无法由 Agent 自行决定时，文档正文后会出现“待确认决策”面板：

1. 阅读问题、选项、Agent 推荐项和未确认影响。
2. Leader 或 Workflow 创建者选择最终选项并确认。
3. 所有必要决策变为 `Resolved` 后，再点击“确认 Design”或“确认 Spec”。

存在 `Open` 决策时，文档确认按钮会被禁用。下游 Spec 或 Build Plan 会继承已经确认的决策；旧版本决策只用于审计，不能继续操作。文档可以下载，下载内容会附带该版本已经确认的决策。

## 6. 审批 Build Plan 和创建任务

### 6.1 审阅分工和任务边界

Build Plan 中应重点检查：

- 任务目标、范围和非目标；
- 验收标准和验证命令；
- 任务依赖、工作量和风险；
- 推荐团队规模；
- 每名成员的匹配理由、画像版本和工作量快照；
- 任务是否符合 `ARCHITECTURE`、`FEATURE` 或 `CHANGE` 的边界。

Leader 可以在批准前编辑分配和负责人。保存会生成新的 Build Plan 版本，并重新记录画像快照。

### 6.2 处理任务拆分警告

当 `TaskGranularityValidator` 发现任务可能拆分过细时，Build Plan 审批区域会显示警告。任务创建前，Leader 可以：

- 选择至少两个 Task，点击“合并选中 Task”，生成新的 Build Plan 版本；
- 点击“保留当前拆分”，填写保留理由；
- 仍有警告时直接批准，也必须填写理由。

任务创建后不能再通过计划合并修改已有任务。所有理由会写入审计日志。

### 6.3 批准并创建 Task

1. Leader 确认 Build Plan 版本、拆分、负责人和 Pull Request 策略。
2. 点击“批准 vN”。普通成员只会看到等待 Leader 批准的状态。
3. 批准后点击“创建任务”；Architecture 会创建并开启子 Workflow，而不是创建开发 Task。
4. Task 创建后，Workflow 详情会显示任务列表和任务包版本。

只有批准的 Build Plan 才能创建 Task。任务包由平台按批准版本和当前 Code Context 生成，并保留 Markdown 和结构化 JSON 两种形式。

## 7. 项目级任务看板

打开左侧“任务看板”即可查看当前项目内所有 Workflow 的任务。看板不再绑定某个 Workflow，也不需要切换成员；每张卡片都会显示：

- Task 编号和标题；
- 当前负责人，未分配时显示“未分配”；
- Task 状态；
- 当前任务包版本；
- 任务分支；
- CI 状态和最近更新时间。

看板固定包含八列：

```text
待处理 | 已分配 | 开发中 | 阻塞 | 待交付 | CI 中 | 已完成 | 已取消/失败
```

看板是只读聚合视图，不支持拖拽改状态。点击或使用键盘确认任务卡会进入任务详情；任务详情中的操作按钮仍按当前用户身份和负责人关系控制。

## 8. 任务详情和任务包

### 8.1 查看任务详情

任务详情显示任务目标、范围、验收标准、测试命令、负责人、任务分支、来源版本、任务包、交付历史、Git/PR/CI 证据和 Blocker 历史。

负责人应先确认：

- 任务分支是否正确；
- Base Commit 和 Code Context 是否符合预期；
- 任务包版本是否为 `CURRENT`；
- 验收标准和测试命令是否可执行。

### 8.2 负责人操作

负责人可以：

1. 复制完整 Markdown 任务包交给本地 Agent，或下载 Markdown/JSON 文件。
2. 在任务状态为 `ASSIGNED` 时点击“确认并开始开发”。
3. 在 `IN_PROGRESS` 时报告 Blocker 或填写交付报告。
4. 提交任务分支、Commit、PR URL（若当前 Workflow 要求）和测试结果。

任务包为 `STALE`、存在未关闭 Blocker 或版本不匹配时，平台会拒绝开始开发或提交交付。任务包被重新生成后，详情页会显示新版本和与上一版本的差异。

### 8.3 非负责人查看规则

非负责人可以从看板进入任务详情并查看任务事实，便于 Leader 或协作者跟进；但不能代替负责人开始开发、报告 Blocker 或提交交付。任务包复制和下载入口仅对负责人开放；较新任务包的版本差异仍可供查看。Leader 可以在未完成任务上重新分配负责人，重新分配后旧任务包可能失效。

## 9. 本地开发和交付

平台不执行本地代码，负责人应在自己的工作区完成以下步骤：

1. 从任务详情复制或下载任务包。
2. 在任务指定分支上开发，不要直接修改或推送默认分支。
3. 按任务包中的测试命令运行检查，并记录实际结果。
4. 提交并推送任务分支。
5. 如果策略要求 Pull Request，在 GitHub 创建指向默认分支的 PR。
6. 在任务详情填写交付报告：任务包 ID、版本和 Hash、分支名、Commit SHA、PR URL、变更文件、测试结果、验收证据和未解决问题。
7. 提交后等待平台同步 Git/PR/CI 事实。

平台会校验 Commit 是否属于目标仓库、是否与任务分支一致、是否与 PR head SHA 一致，以及 CI 是否针对该 Commit 通过。仅填写一个不存在的 SHA 或 PR 地址不能完成交付。

## 10. Blocker 和需求澄清

负责人在任务处于 `IN_PROGRESS` 时可以报告 Blocker。报告时填写：

- 原因类型；
- 一句话摘要；
- 已观察到的现象和影响；
- 希望 Leader 明确回答的问题。

报告后任务进入 `BLOCKED`，Workflow 不会被无条件整体阻塞。Leader 在任务详情填写处理结论后，可以“解决并生成新任务包”或“取消 Blocker”。负责人确认新包后才能恢复开发。所有 Blocker 的创建、处理和任务包变化都会进入时间线和审计记录。

## 11. Git、CI 和通知

### 11.1 Git/CI 证据

任务详情的证据区域展示交付记录、Git 操作、Pull Request 和 CI Runs。外部状态可能因为 Webhook 延迟或网络问题暂时未更新，可以等待自动轮询或使用页面刷新/CI 重试。不要把页面上的旧状态当作新的 Commit 已通过。

`CI_REQUIRED` 项目中，当前 Commit 对应的必要 CI 检查通过后才允许完成任务。CI 失败时先阅读检查详情，修复后重新推送并等待新的 Run；只重试没有修复代码的旧 Run 通常不能解决失败。

### 11.2 站内通知

“通知”页面集中显示任务分配、重新分配、Blocker、交付和 Build Plan 审批提醒。打开通知后可点击“标记已读”。未读数量会显示在左侧导航。

## 12. 审计日志和历史版本

Leader 可以打开“审计日志”查看项目级时间线，Workflow 创建者或 Leader 也可以在 Workflow 详情查看 Workflow 时间线。审计记录包含操作人、实体、时间和结构化详情；审计日志不可编辑或删除。

文档、Build Plan、任务包、分配、交付和外部事实都采用版本或历史记录方式保存。发现错误时应通过编辑生成新版本或执行具名业务操作，不要期待直接覆盖旧记录。

## 13. 关闭、取消和归档

- Workflow 只有在状态机满足关闭条件时才能关闭。
- CI 必选项目必须先完成当前 Commit 的必要 CI 检查。
- Architecture Workflow 按架构基线规则关闭；Feature/Change 需要完成其必要任务和交付。
- 取消 Workflow 或 Task 是具名操作，不会自动删除分支、PR 或历史证据。
- 归档项目后不能创建新的 Workflow 或任务，但历史任务、交付、通知和审计仍可追溯。

## 14. 常见问题

### 14.1 生成按钮不可用

检查 Workflow 状态、Code Context 和当前 AgentRun：

- Code Context 不为 `CURRENT`：先同步仓库索引，再刷新 Workflow Code Context；
- Run 为 `QUEUED` 或 `RUNNING`：等待当前生成完成；
- Build Plan 重新生成显示“生成中”：这是防止重复提交的正常状态；
- 没有 Leader 权限：Build Plan 批准和部分重新生成操作不会显示。

### 14.2 无法开始开发或提交交付

检查当前用户是否为负责人、任务包是否为 `CURRENT`、是否有开放 Blocker、任务包 Hash/版本是否匹配，以及 Commit、分支、PR 和 CI 是否绑定到同一任务。

### 14.3 看不到项目或任务

确认顶部选择的是正确项目，并确认当前账号仍是该项目的 ACTIVE 成员。项目资源按项目隔离，其他项目的 Workflow、Task 和审计记录不会显示。

### 14.4 CI 或 Git 状态长时间未更新

先确认 GitHub 仓库、Token、Webhook 和 Actions 本身可用，再刷新页面或等待轮询。若 CI 运行器、Docker 或外部网络不可用，应先处理运行环境问题，不要仅凭一次超时判断代码失败。

## 15. 使用边界和安全要求

- 不要把 Git Token、Agent API Key 或密码写入任务包、提交记录、截图或聊天消息。
- 本地 Agent Key 只保存在成员自己的电脑上；平台不会代为保管。
- 不要在浏览器开发者工具中伪造负责人、项目或 Commit；后端会按项目成员和资源归属重新校验。
- 不要直接推送默认分支或使用 Force Push；按任务包要求使用任务分支。
- 对外部服务状态、Webhook 和 CI 结果，以平台同步到的 Commit 绑定事实为准。

## 16. 一页式操作清单

### Leader

```text
[ ] 创建项目并确认 GitHub 仓库、默认分支
[ ] 邀请成员，确认所有成员完成项目画像
[ ] CI_NOT_CONFIGURED 项目先完成 CI Bootstrap
[ ] 创建普通 Workflow，选择正确 Intent 级别
[ ] 同步仓库索引并刷新 Workflow Code Context
[ ] 生成并审阅 Design、Spec、Build Plan
[ ] 处理待确认决策和任务拆分警告
[ ] 批准 Build Plan 并创建 Task
[ ] 在项目看板和任务详情跟进负责人、Blocker、PR、CI
[ ] 满足关闭条件后关闭 Workflow
```

### Member/负责人

```text
[ ] 加入项目并完成自己的能力画像
[ ] 查看项目看板，确认负责人字段和任务状态
[ ] 从自己负责的任务详情复制或下载任务包
[ ] 确认任务包并在指定任务分支开发
[ ] 运行任务包中的测试命令
[ ] 推送 Commit，按策略创建 PR
[ ] 提交完整交付报告并等待 Git/CI 校验
[ ] 遇到不明确事项先报告 Blocker
```
