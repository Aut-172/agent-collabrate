# 架构决策记录

## ADR-001：平台只做任务编排，代码 Agent 在成员本地执行

### 状态

已接受。

### 决策

平台侧 Agent 只负责 Design、Spec、Build Plan 等文档和计划生成。成员使用本地 Codex CLI 或其他 Agent 完成代码阅读、修改、测试和 Git 操作。

### 原因

- 普通服务端 API 调用不会自动获得成员电脑和本地仓库权限；
- 平台远程执行代码需要额外的 Runtime、工具调用层和沙箱；
- MVP 优先验证协作编排价值；
- 成员可以继续使用现有本地开发环境。

### 影响

- 任务交接必须结构化并版本化；
- 平台不能实时观察本地 Agent；
- Blocker、测试结果和交付信息需要成员回填；
- 本地凭证不进入平台。

## ADR-002：平台 Agent 调用采用异步运行记录

### 状态

已接受。

### 决策

每次 Agent 调用创建 AgentRun 和 OutboxJob，HTTP 请求返回 202，不等待模型完成。

### 原因

- 模型调用可能超时或持续较长时间；
- 需要重试、取消、错误查看和审计；
- 同步请求容易造成线程占用和重复提交。

### 影响

- 前端需要查询运行状态；
- 后端需要 Worker 和任务回收；
- AgentRun 状态与 Workflow 状态分离。

## ADR-003：Agent 生成的计划由 Leader 审批

### 状态

已接受。

### 决策

Agent 生成任务和人员分配建议，Leader 可以通过表单/表格或高级 JSON 编辑修改，只有批准版本才能创建 Task。

### 原因

- Agent 的任务拆分和人员匹配不是绝对正确；
- 责任和最终决策必须由人承担；
- 结构化 Plan 便于校验、版本和审计。

### 影响

- Build Plan 必须有 JSON Schema；
- Plan 修改会产生新版本；
- 批准动作绑定具体版本。

## ADR-004：任务包采用 Markdown + JSON

### 状态

已接受。

### 决策

平台生成同一版本的 Markdown 和 JSON 任务包。Markdown 面向人和本地 Agent，JSON 面向平台校验和未来 CLI。

### 原因

- 纯自由文本容易丢失范围、基线和验收标准；
- 纯 JSON 不便于成员直接阅读；
- 双格式可以兼顾可用性和规范性。

### 影响

- 任务包需要 Schema、哈希和版本；
- 任务包变更会使旧包 `STALE`；
- 开始开发和提交交付都必须校验版本。

## ADR-005：任务包中的 Git 策略为声明性约束

### 状态

已接受。

### 决策

任务包明确允许创建分支、Commit、Push 任务分支和可选创建 PR，禁止 Push 默认分支、Force Push、Merge 和删除远程分支。

### 原因

- 本地 Agent 在得到许可后可以执行 Git 指令；
- 成员需要一个完整的本地交付流程；
- 任务包可以减少误操作，但不能替代本地安全机制。

### 影响

- GitHub 分支保护仍然必须配置；
- 平台不把 Git Token 传给 Agent；
- 成员需要审阅 Diff 和测试结果。

## ADR-006：MVP 纳入轻量任务看板

### 状态

已接受。

### 决策

看板直接映射 Task.status，不创建独立看板状态，不支持拖拽自动改状态。

### 原因

- 任务列表可以完成管理，但不利于快速理解进度；
- 看板的边际实现成本较低；
- 复用状态机可以避免引入第二套状态。

### 影响

- 增加 Board 查询接口；
- 看板展示阻塞和 CI 状态；
- 状态仍由具名业务动作改变。

## ADR-007：GitHub 优先，Webhook + 轮询

### 状态

已接受。

### 决策

MVP 先支持 GitHub 和 GitHub Actions。Webhook 用于实时更新，轮询和手动同步用于网络不稳定或事件丢失时恢复。

### 原因

- 同时支持多个 Git 平台会扩大适配和测试范围；
- Webhook 低延迟，轮询更容易兜底；
- 国内公网访问外部服务可能不稳定。

### 影响

- 所有外部调用要异步化；
- 必须处理签名、幂等、重试、限流和 UNKNOWN；
- 网络失败不能被解释为 CI 通过。

## ADR-008：完成状态必须绑定当前 Commit 的 CI

### 状态

已接受。

### 决策

Task 只有在当前交付 Commit 的必要 CI 检查全部通过且没有未解决 Blocker 时才能完成。Workflow 在所有必要 Task 完成并经 Leader 关闭后完成。

### 原因

- Push 成功不代表代码可交付；
- 旧 Commit 的成功不能证明新 Commit；
- Workflow 完成和 Task 完成是两个层次。

### 影响

- CIRun 必须保存 head SHA；
- 新 Commit 会使旧 CI 结果失效；
- 默认不提供人工强制完成。

## ADR-009：文档和任务包不可变版本化

### 状态

已接受。

### 决策

Design、Spec、Build Plan、Task 和 TaskPackage 不直接覆盖，所有修改生成新版本。

### 原因

- 需要追溯成员基于哪一版上下文开发；
- 需求变化后必须能识别旧任务包；
- 审计和返工需要保留历史。

### 影响

- 数据模型增加版本字段和来源关系；
- 更新会触发 stale 检查和通知；
- 数据量会增长，需要后续保留策略。

## ADR-010：MVP 使用数据库 Outbox，不引入消息队列

### 状态

已接受。

### 决策

Agent、Git、CI 后台任务使用 PostgreSQL 中的 OutboxJob 和 Spring Worker。未来规模增大时再替换为消息队列。

### 原因

- MVP 并发量有限；
- 减少部署组件；
- 数据库任务和业务写入可以在同一事务中创建。

### 影响

- 需要行锁、超时回收和幂等；
- 单体扩展能力有限；
- 必须限制并发和外部 API 速率。

## ADR-011：能力画像属于项目成员关系，Leader 也参与开发

### 状态

已接受。

### 决策

用户的登录身份保存在 `users`。用户加入项目后，在 `project_members` 中填写该项目专属的能力与职责画像。Leader 和 Member 都是可被 Agent 分配任务的开发成员；Leader 额外拥有项目治理权限。

### 原因

- 同一用户在不同项目中的职责和能力可能不同；
- Agent 分配需要项目上下文，而不是全局用户信息；
- Leader 本身也参与开发，不能被排除在任务候选人之外；
- 将画像放在项目成员关系中可以实现项目隔离和版本追踪。

### 影响

- `project_members` 增加 `capability_profile` 和画像完成状态；
- 成员加入项目时必须填写画像；
- Agent 生成分配建议时读取所有已完成画像；
- `task_assignments` 保存分配时的画像快照和理由；
- 成员后续更新画像不改变历史分配依据；
- Leader 被分配任务时遵循与 Member 相同的本地开发、交付和 CI 规则。

## ADR-012：Intent 层级与生命周期分离

### 状态

已接受。

### 决策

Intent 使用 `ARCHITECTURE`、`FEATURE`、`CHANGE` 三个层级字段。层级决定 Design/Spec/Build Plan 的处理管线，但不新增一套独立状态机。

### 原因

- 架构级需求、功能级需求和局部变更的产物和完成条件不同；
- 复用生命周期状态可以避免状态爆炸；
- 父子 Intent 可以表达架构基线到具体 Feature/Change 的分解关系。

### 影响

- Workflow 增加 `intent_level` 和可选 `parent_workflow_id`；
- Architecture 完成不等待代码交付；
- Feature/Change 进入开发分工和 Task 交付流程。

## ADR-013：Architecture 不产生开发分工

### 状态

已接受。

### 决策

Architecture 只输出架构边界、约束、非功能需求、风险和子 Intent 建议，不输出开发负责人、TaskAssignment 或代码交付型 Task。

### 原因

架构设计阶段的参与者建议属于评审协作，不等同于实现分工；过早分配会把架构讨论和代码执行混在一起。

## ADR-014：Feature/Change 的分工由 AI 建议、Leader 审批

### 状态

已接受。

### 决策

Feature 和 Change 必须生成 AI staffing recommendation。Feature 通常比 Change 推荐更多成员，但该规则是软约束。Leader 可以修改人数、模式、任务拆分和负责人，批准后才创建实际 TaskAssignment。

### 原因

- Feature 通常跨模块、验收面更广，需要更多并行协作；
- Change 通常是局部修改，单人负责更高效；
- 实际复杂度存在例外，固定人数会误导分工；
- Leader 需要保留最终治理和责任边界。

## ADR-015：AI 分工使用画像和工作量快照

### 状态

已接受。

### 决策

AI 分工至少综合 Intent 层级、任务范围、依赖、`effort_points`、成员能力画像、可投入容量和未完成任务工作量。批准分配时保存画像版本、画像快照、工作量快照、匹配理由和评分。

### 原因

只按技能匹配会导致任务集中到少数成员；只按任务数量又无法反映任务规模。快照可以解释历史决策，也避免成员后续更新画像改变历史事实。

### 影响

- `tasks` 增加 `effort_points`；
- `project_members` 增加 `weekly_capacity_points` 和可分配状态信息；
- `task_assignments` 保存 `workload_snapshot` 和 `assignment_score`；
- 已开始执行的任务不因工作量变化自动换人。

## ADR-016：从零项目使用 CI Bootstrap 建立完成门禁

### 状态

已接受。

### 决策

项目初始可以没有代码框架或 CI。项目状态标记为 `CI_NOT_CONFIGURED`，先通过一个受限的 `FEATURE + CI_BOOTSTRAP` Workflow 提交最小工程骨架、构建测试入口并验证第一条 CI 管线。Bootstrap 成功后项目切换为 `CI_REQUIRED`，普通 Feature/Change 必须满足当前 Commit 的 CI 才能完成。

Bootstrap 只能由项目 Leader 通过专用接口创建，任务固定初始分配给该 Workflow 的创建者 Leader。该模式只服务于建立初始工程入口和第一条 CI；项目进入 `CI_REQUIRED` 后，后续 CI 配置修改必须作为普通 Change Workflow 执行。

### 原因

- 如果新项目从第一天就要求 CI，会产生“没有 CI 就无法通过 CI”的循环；
- 如果允许所有早期 Workflow 永久免 CI，后续门禁很容易失效；
- 用一次性 Bootstrap 把“建立门禁”和“遵守门禁”分开，既允许从零开始，也保留可验证的完成条件。

### Bootstrap 完成条件

- 当前 Bootstrap Commit 属于目标仓库；
- CI 配置存在于该 Commit；
- Provider 已识别 CI 配置；
- 至少一个真实 CI 检查以该 Commit 为 head SHA 并通过；
- 没有未解决 Blocker；
- Leader 关闭 Bootstrap 后，项目原子地变为 `CI_REQUIRED`。

### 影响

- Project 增加 `ci_status`；
- Workflow 增加 `completion_mode`；
- 普通 Workflow 不能在 `CI_NOT_CONFIGURED` 时直接绕过 Bootstrap；
- Architecture 无代码交付，可使用 `ARCHITECTURE_BASELINE` 完成模式；
- Bootstrap 不能作为普通 Feature/Change 的通用免检开关。

## ADR-017：平台 Agent 生成文档前必须获取代码上下文

### 状态

已接受。

### 决策

引入 `CodeContextProvider` 和 `CodeContextOrchestrator`。平台 Agent 生成 Design、Spec 和 Build Plan 前，必须先获得版本化、可追溯的代码上下文证据。MVP 当前扩展优先使用 Git Provider 建立 Repo Inventory，再由平台 Agent 生成 Context Plan，Orchestrator 按计划多轮、受控地读取相关文件和 Diff。接口上预留 `LocalAgentCodeContextProvider`，未来可由本地 Connector 调用 Codex CLI 返回代码证据。

### 原因

- 只凭 Intent 无法生成可靠的项目级 Design 和 Spec；
- 纯摘要快照容易丢失真实代码约束；
- Git Provider 无法在没有 Intent 语义引导时自主判断相关文件；
- 平台 Agent 需要先看 Repo Inventory 再决定定向读取哪些文件；
- 让本地 Agent 直接生成最终 Design/Spec 会模糊平台 Agent 的文档责任；
- Git Provider 轻量读取仓库的实现成本低于完整本地 Connector；
- 平台仍需统一版本化、Schema 校验、审批和审计。

### 影响

- AgentRun 需要绑定使用的 Code Context 版本；
- 需要保存 Repo Inventory、Context Plan 和 Code Evidence；
- Design、Spec、Build Plan 应保留关键证据引用；
- TaskPackage 需要包含 `codeContextVersionId`、`contextPlanId`、`baseCommitSha` 和代码证据摘要；
- 默认分支 Commit 变化时，旧 Code Context 可被标记为 `STALE`；
- Git Provider 网络失败时不能静默生成无代码证据的正式文档；
- Git Provider 实现中不能包含自主语义相关性判断；
- 本地 Agent Provider 未来只返回 Code Evidence，不替代平台 Agent 的正式文档生成职责。

## ADR-018：Provider 按 Profile 隔离，生产未配置时显式失败

### 状态

已接受。

### 决策

Mock Agent/Git/CI/Code Context Provider 仅在 `test` 或 `mock-provider` Profile 加载。生产环境没有真实 Agent Provider Adapter 时加载未配置占位实现，生成请求以明确错误结束，不返回 Mock 文档或伪造外部事实。

### 原因

- 测试数据不能进入生产业务流程；
- 生产启动应能暴露缺失配置，而不是静默使用 Mock；
- 外部 Provider 失败不能被解释为成功。
