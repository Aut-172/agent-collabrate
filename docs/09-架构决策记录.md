# 架构决策记录

## ADR-001：平台只做任务编排，代码 Agent 在成员本地执行

### 状态

已接受。

### 决策

平台侧 Agent 只负责 Design、Spec、Build Plan 等文档和计划生成。成员使用本地 Codex CLI 或其他 Agent 完成代码阅读、修改、测试和 Git 操作。

### 原因

- 普通服务端 API 调用不会自动获得成员电脑和本地仓库权限；
- 平台远程执行代码需要额外的 Runtime、工具调用层和沙箱；
- MVP 优先验证协作编排价值；
- 成员可以继续使用现有本地开发环境。

### 影响

- 任务交接必须结构化并版本化；
- 平台不能实时观察本地 Agent；
- Blocker、测试结果和交付信息需要成员回填；
- 本地凭证不进入平台。

## ADR-002：平台 Agent 调用采用异步运行记录

### 状态

已接受。

### 决策

每次 Agent 调用创建 AgentRun 和 OutboxJob，HTTP 请求返回 202，不等待模型完成。

### 原因

- 模型调用可能超时或持续较长时间；
- 需要重试、取消、错误查看和审计；
- 同步请求容易造成线程占用和重复提交。

### 影响

- 前端需要查询运行状态；
- 后端需要 Worker 和任务回收；
- AgentRun 状态与 Workflow 状态分离。

## ADR-003：Agent 生成的计划由 Leader 审批

### 状态

已接受。

### 决策

Agent 生成任务和人员分配建议，Leader 可以通过表单/表格或高级 JSON 编辑修改，只有批准版本才能创建 Task。

### 原因

- Agent 的任务拆分和人员匹配不是绝对正确；
- 责任和最终决策必须由人承担；
- 结构化 Plan 便于校验、版本和审计。

### 影响

- Build Plan 必须有 JSON Schema；
- Plan 修改会产生新版本；
- 批准动作绑定具体版本。

## ADR-004：任务包采用 Markdown + JSON

### 状态

已接受。

### 决策

平台生成同一版本的 Markdown 和 JSON 任务包。Markdown 面向人和本地 Agent，JSON 面向平台校验和未来 CLI。

### 原因

- 纯自由文本容易丢失范围、基线和验收标准；
- 纯 JSON 不便于成员直接阅读；
- 双格式可以兼顾可用性和规范性。

### 影响

- 任务包需要 Schema、哈希和版本；
- 任务包变更会使旧包 `STALE`；
- 开始开发和提交交付都必须校验版本。

## ADR-005：任务包中的 Git 策略为声明性约束

### 状态

已接受。

### 决策

任务包明确允许创建分支、Commit、Push 任务分支和可选创建 PR，禁止 Push 默认分支、Force Push、Merge 和删除远程分支。

### 原因

- 本地 Agent 在得到许可后可以执行 Git 指令；
- 成员需要一个完整的本地交付流程；
- 任务包可以减少误操作，但不能替代本地安全机制。

### 影响

- GitHub 分支保护仍然必须配置；
- 平台不把 Git Token 传给 Agent；
- 成员需要审阅 Diff 和测试结果。

## ADR-006：MVP 纳入轻量任务看板

### 状态

已接受。

### 决策

看板直接映射 Task.status，不创建独立看板状态，不支持拖拽自动改状态。

### 原因

- 任务列表可以完成管理，但不利于快速理解进度；
- 看板的边际实现成本较低；
- 复用状态机可以避免引入第二套状态。

### 影响

- 增加 Board 查询接口；
- 看板展示阻塞和 CI 状态；
- 状态仍由具名业务动作改变。

## ADR-007：GitHub 优先，Webhook + 轮询

### 状态

已接受。

### 决策

MVP 先支持 GitHub 和 GitHub Actions。Webhook 用于实时更新，轮询和手动同步用于网络不稳定或事件丢失时恢复。

### 原因

- 同时支持多个 Git 平台会扩大适配和测试范围；
- Webhook 低延迟，轮询更容易兜底；
- 国内公网访问外部服务可能不稳定。

### 影响

- 所有外部调用要异步化；
- 必须处理签名、幂等、重试、限流和 UNKNOWN；
- 网络失败不能被解释为 CI 通过。

## ADR-008：完成状态必须绑定当前 Commit 的 CI

### 状态

已接受。

### 决策

Task 只有在当前交付 Commit 的必要 CI 检查全部通过且没有未解决 Blocker 时才能完成。Workflow 在所有必要 Task 完成并经 Leader 关闭后完成。

### 原因

- Push 成功不代表代码可交付；
- 旧 Commit 的成功不能证明新 Commit；
- Workflow 完成和 Task 完成是两个层次。

### 影响

- CIRun 必须保存 head SHA；
- 新 Commit 会使旧 CI 结果失效；
- 默认不提供人工强制完成。

## ADR-009：文档和任务包不可变版本化

### 状态

已接受。

### 决策

Design、Spec、Build Plan、Task 和 TaskPackage 不直接覆盖，所有修改生成新版本。

### 原因

- 需要追溯成员基于哪一版上下文开发；
- 需求变化后必须能识别旧任务包；
- 审计和返工需要保留历史。

### 影响

- 数据模型增加版本字段和来源关系；
- 更新会触发 stale 检查和通知；
- 数据量会增长，需要后续保留策略。

## ADR-010：MVP 使用数据库 Outbox，不引入消息队列

### 状态

已接受。

### 决策

Agent、Git、CI 后台任务使用 PostgreSQL 中的 OutboxJob 和 Spring Worker。未来规模增大时再替换为消息队列。

### 原因

- MVP 并发量有限；
- 减少部署组件；
- 数据库任务和业务写入可以在同一事务中创建。

### 影响

- 需要行锁、超时回收和幂等；
- 单体扩展能力有限；
- 必须限制并发和外部 API 速率。

## ADR-011：能力画像属于项目成员关系，Leader 也参与开发

### 状态

已接受。

### 决策

用户的登录身份保存在 `users`。用户加入项目后，在 `project_members` 中填写该项目专属的能力与职责画像。Leader 和 Member 都是可被 Agent 分配任务的开发成员；Leader 额外拥有项目治理权限。

### 原因

- 同一用户在不同项目中的职责和能力可能不同；
- Agent 分配需要项目上下文，而不是全局用户信息；
- Leader 本身也参与开发，不能被排除在任务候选人之外；
- 将画像放在项目成员关系中可以实现项目隔离和版本追踪。

### 影响

- `project_members` 增加 `capability_profile` 和画像完成状态；
- 成员加入项目时必须填写画像；
- Agent 生成分配建议时读取所有已完成画像；
- `task_assignments` 保存分配时的画像快照和理由；
- 成员后续更新画像不改变历史分配依据；
- Leader 被分配任务时遵循与 Member 相同的本地开发、交付和 CI 规则。
