# MVP 前端设计规范与页面说明

## 1. 设计目标

前端定位为工程协作和交付管理工具，强调：

```text
清晰、克制、高信息密度、状态优先、操作可追踪
```

不做营销型首页，不做聊天窗口式主界面，不把复杂信息隐藏在多层弹窗中。

## 2. 视觉方向

- 浅色主题优先，预留深色主题；
- 主色使用蓝色或深靛蓝；
- 成功使用绿色，警告使用琥珀色，失败/阻塞使用红色；
- 背景使用浅灰，正文使用深灰；
- 边框和分割线使用中性灰；
- 卡片圆角不超过 8px；
- 避免大面积渐变、装饰性光晕和过度圆角；
- 状态不能只依赖颜色，必须同时显示文字或图标。

## 3. 全局布局

### 桌面端

```text
┌─────────────────────────────────────────────────────┐
│ 顶部栏：项目切换 | 页面标题 | 通知 | 用户菜单         │
├──────────────┬──────────────────────────────────────┤
│ 左侧导航     │ 主内容区                             │
│ 项目概览     │                                      │
│ 工作流       │                                      │
│ 任务看板     │                                      │
│ 文档         │                                      │
│ 项目成员     │                                      │
│ 审计日志     │                                      │
│ 项目设置     │                                      │
└──────────────┴──────────────────────────────────────┘
```

- 左侧导航固定；
- 顶部栏固定；
- 主内容区独立滚动；
- 顶部项目切换器显示当前项目；
- 项目设置和治理操作与日常开发操作分开。

### 移动端

- 侧边栏改为抽屉或底部导航；
- 看板允许横向滚动；
- 关键状态和下一步操作保持在首屏；
- 不强行把桌面端多栏布局压缩成窄列。

## 4. 全局导航

```text
项目概览
工作流
任务看板
文档
项目成员
审计日志
项目设置
```

导航项可以根据权限隐藏或置灰，但后端权限仍必须独立校验。

## 5. 页面说明

### 5.1 项目概览

显示：

- 项目健康状态；
- CI 状态：未配置 / Bootstrap 验证中 / 已启用门禁；
- 进行中的 Workflow；
- 待 Leader 处理事项；
- Blocked Task；
- CI 失败和运行中 CI；
- 最近交付；
- 最近同步时间。

建议用一行摘要表达项目状态：

```text
12 个任务进行中 · 2 个阻塞 · 3 个 CI 检查中 · 最近同步 2 分钟前
```

当项目为 `CI_NOT_CONFIGURED` 时，项目概览必须显示明确的 Bootstrap 入口：

```text
项目尚未初始化工程与 CI · 先完成初始化
```

普通 Feature/Change 的关闭按钮应显示为不可用，并说明需要先完成 Bootstrap；Architecture Workflow 仍可按架构基线规则关闭。

### 5.1A 初始化工程与 CI

创建 Workflow 时先选择“普通工作流”或“初始化工程与 CI”。普通工作流继续选择 Architecture、Feature 或 Change；选择“初始化工程与 CI”后不再向用户展示 Intent 层级，请求体只提交标题和描述，服务端固定按 Feature 创建。该选项向 Member 展示但禁用，并提示只有 Leader 可以创建。项目已启用 CI 或已有进行中的 Bootstrap 时也必须禁用并说明原因。

Bootstrap 页面显示：

- 当前项目 `ci_status`；
- Bootstrap Workflow 和任务；
- CI 配置文件是否存在于当前 Commit；
- Provider 是否已识别配置；
- 当前 Bootstrap Commit；
- 引导检查的运行状态和详情链接；
- 关闭 Bootstrap 的前置条件。

Bootstrap 覆盖最小工程骨架、构建/测试入口和第一条 CI，任务固定初始分配给创建该 Workflow 的 Leader。已有框架的仓库可以只填写缺失部分；后续修改 CI 配置不使用该入口，而是创建普通 Change Workflow。

页面不提供“手工标记 CI 通过”按钮。所有通过状态必须来自 Git/CI Provider 同步。

### 5.2 Workflow 详情

顶部：

- 标题；
- Workflow 状态；
- 健康状态；
- 创建者；
- 当前版本；
- 当前下一步操作。

主体：

```text
阶段条
  -> Design / Spec / Plan
文档区域
  -> 当前版本、历史版本、确认人
任务区域
  -> 任务摘要和看板入口（Feature/Change）
时间线
  -> 审批、分配、阻塞、交付、CI 和审计
```

根据 `intent_level` 调整页面：

- Architecture：突出架构目标、系统边界、约束、非功能需求、风险和子 Intent；不显示开发负责人或分工表；
- Feature：显示功能任务、推荐团队规模、成员匹配理由、工作量/容量和风险；
- Change：显示局部任务、推荐单人/双人模式、成员匹配理由和风险。

阶段条：

```text
Intent -> Design -> Spec -> Plan -> Tasks -> Development -> Delivery -> CI -> Done
```

每个阶段显示状态、版本、最后修改人和更新时间。

### 5.3 任务看板

列：

```text
待处理 | 已分配 | 开发中 | 阻塞 | 待交付 | CI 中 | 已完成 | 已取消/失败
```

任务卡显示：

- Task 编号和标题；
- 负责人；
- Workflow；
- 当前任务包版本；
- 分支；
- PR 状态；
- CI 状态；
- 最近更新时间。

MVP 不支持拖拽改变状态。状态通过“开始开发”“报告阻塞”“提交交付”等具名操作改变。

### 5.4 任务详情

顶部显示：

```text
任务标题 | Task 状态 | 负责人 | 任务包版本
```

主体分栏：

- 左侧：目标、范围、非目标、验收标准、测试命令；
- 右侧：任务包状态、分支、Commit、PR、CI、Blocker；
- 底部：交付历史和审计时间线。

必须突出：

```text
当前任务包是否有效
当前 Commit 是什么
当前 CI 是否对应这个 Commit
```

### 5.5 任务包确认

任务包不需要成员重新上传。页面显示：

```text
当前任务包：v3
状态：CURRENT
内容哈希：sha256:...
你的最近确认：v3
```

按钮：

- 查看任务包；
- 下载 Markdown；
- 下载 JSON；
- 复制任务指令；
- 确认并开始开发；
- 查看旧版本差异。

如果任务包更新：

```text
旧版本：STALE
新版本：CURRENT
```

页面必须展示差异，并要求成员确认新版本后才能继续。

### 5.6 交付页面

使用分步确认，而不是单一提交按钮：

```text
1. 任务包
2. Final Report
3. Git 信息
4. 平台校验
5. 提交交付
```

提交前显示：

```text
任务包版本：v3
任务包哈希：sha256:...
最近确认版本：v3
分支：agent/wf-42/task-001
Commit：abcdef1
PR：#18
Git 校验：通过
CI 状态：等待中
```

前端可以自动从 Final Report 提取分支、Commit 和 PR，但最终以服务端校验结果为准。

预检查：

```text
[通过] 当前负责人正确
[通过] 当前任务包仍有效
[通过] 最近确认版本匹配
[通过] Final Report 版本和哈希匹配
[通过] Commit 存在且属于目标仓库
[通过] PR head SHA 匹配
[等待] CI 检查
```

### 5.7 计划审批

默认使用表格/表单编辑，不直接展示原始 JSON：

```text
任务 | 描述 | 负责人 | 画像摘要 | 当前工作量/容量 | 分配理由 | 范围 | 验收标准 | Git 策略
```

支持：

- AI 建议与 Leader 修改对比；
- 显示 Intent 层级对应的计划类型；
- Feature/Change 显示推荐分工模式、推荐人数、人数依据、工作量快照和警告；
- Architecture 显示架构边界、约束、风险和子 Intent，不显示开发分工表；
- 负责人选择；
- 分配理由编辑；
- 画像摘要查看；
- 高级 JSON 编辑；
- JSON Schema 校验；
- 保存新版本；
- 批准具体版本。

### 5.8 项目成员和能力画像

成员页面显示：

- 用户名；
- 项目角色；
- 能力摘要；
- 职责范围；
- 技术标签；
- 擅长任务类型；
- 限制和偏好；
- 当前任务。

画像编辑使用结构化表单，不设计成完整简历页面。

Leader 和 Member 都可以编辑自己的画像。Leader 可以查看项目成员画像，但不能无痕代替成员修改。

## 6. 交互规范

### 6.1 下一步操作

每个详情页都要明确显示：

```text
当前状态：BUILD_PLAN_PROPOSED
下一步：Leader 审批构建计划
```

或：

```text
当前状态：BLOCKED
下一步：等待 Leader 回复问题
```

### 6.2 状态表达

同时使用文字、颜色和图标：

| 状态 | 建议图标 | 颜色 |
|---|---|---|
| 成功/通过 | CheckCircle | 绿色 |
| 等待 | Clock3 | 中性灰/蓝 |
| 阻塞 | CircleAlert | 红色/琥珀色 |
| 失败 | CircleX | 红色 |
| 过期 | History | 琥珀色 |
| PR | GitPullRequest | 蓝色 |
| Commit | GitCommitHorizontal | 中性灰 |
| 负责人 | UserRound | 中性灰 |
| 文档 | FileText | 中性灰 |

优先使用现有图标库，例如 Lucide。陌生图标提供 Tooltip。

### 6.3 操作反馈

- 长耗时操作显示运行状态和 `runId`；
- 失败信息说明原因和可执行的下一步；
- 版本冲突使用 409 页面状态，而不是普通 Toast；
- 危险操作需要确认；
- 操作成功后更新相关状态、时间线和通知；
- 不通过颜色单独表达权限或失败。

## 7. 响应式和信息密度

- 桌面端优先支持 1280px 及以上宽度；
- 1024px 左右保持双栏可用；
- 移动端重点保证任务详情、状态和交付流程；
- 表格允许横向滚动，不压缩到不可读；
- 看板列使用稳定宽度，避免卡片内容造成布局跳动；
- 文本超长时换行或折叠，不覆盖相邻内容；
- 不使用随视口宽度线性缩放的字体。

## 8. 当前技术实现

仓库已固定使用 Vite + React + JavaScript，并使用 `lucide-react` 图标。前端工程位于 `frontend/`：

```text
frontend/
  index.html
  vite.config.js       # /api 代理到后端 8080
  src/main.jsx         # 登录、项目、Workflow、看板、成员、通知、审计
  src/styles.css       # 桌面/移动响应式样式
```

启动命令：`cd frontend; npm install; npm run dev`。生产构建命令：`npm run build`。

当前已实现登录、项目切换、项目概览、Workflow 列表、8 列只读看板、成员列表、通知列表/标记已读和审计日志页面。任务卡展示负责人、任务包版本、分支、CI 和更新时间；状态变更仍通过后端具名业务 API。

## 8.1 后续页面补齐项

以下页面规范仍是后续迭代目标，当前 React MVP 尚未提供完整编辑交互：Workflow 文档版本编辑/确认、Build Plan 表单审批、任务包复制/下载/差异、Blocker 报告和处理、Final Report/TaskDelivery 分步提交、Git/PR/CI 详情和完整审计时间线。

## 8.2 前端技术建议（历史）

如果项目尚未固定前端技术栈，建议：

```text
React + TypeScript + Vite
Tailwind CSS
现有组件库或 shadcn/ui
Lucide Icons
TanStack Query
React Hook Form + Zod
```

如果主 Agent 已经选择其他技术栈，优先遵循现有项目结构，不为视觉规范引入第二套框架。

## 9. MVP 前端不做

- 拖拽驱动状态机；
- 自定义看板列；
- 复杂任务依赖图；
- 多种主题和高度定制化皮肤；
- 实时协作编辑；
- 平台远程控制本地 Agent；
- 自动上传或同步成员本地任务包；
- 自动合并 PR。
